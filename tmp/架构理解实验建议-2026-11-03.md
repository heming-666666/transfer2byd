# 架构理解实验建议（AR-01 – AR-10，2026-11-03）

> **依据**：用户贴回的《H800-V4 实验室 · 已完成实验记录》（生成 2026-11-04：完成 17 项，部分完成 6 项，BLOCKED 3 类），本包 E01–E23 文档，以及研究文档 `markdown/ai-infra-research/09-创新点全景与下一步研究计划-2026-11-01.md` 第 6.2–6.3 节（P1–P5 与按周计划）。
>
> **为什么要另做一批**：E01–E24 基本测完了推理引擎的“旋钮”（并行、量化、CUDA graph、调度），但主力负载是 qwen3-8b，它是普通的稠密 GQA 模型，碰不到 DeepSeek-V4.1-Flash-1017 和 GLM-5.3-Flash 的架构设计。本批实验每次只改一个和架构有关的变量，并且**先手算预期、再实测对照**，目标是看懂“模型为什么这样设计、这样设计给推理系统带来了什么”。
>
> **编号**：用 AR（architecture），避免和 GPU 机上已经用掉的 E24（litellm 网关）冲突。本文件只是规划，**没有在本机执行**；结果回传后，在各节末尾的“本机实测记录”写一行总结，并同步对应的 E 文档。

## 0. 开跑前先核对的三件事

| # | 问题 | 现有证据 | 怎么核对 | 为什么重要 |
|---|---|---|---|---|
| 0.1 | 卡到底是 H800 还是 H100 | 记录写 H800；用户说 8×H100。E15 单对 NVLink 单向实测 339.8 GB/s，超过 H800 的公开规格（NVLink 400 GB/s 双向，约 200 GB/s 单向），更接近 H100（900 GB/s 双向） | `nvidia-smi -q \| grep -i "product name"`；`nvidia-smi nvlink -s`（看链路数和每条速率） | 决定 E02/E05/E15 的通信结论怎么解读；研究问题 R5（“H800 带宽只有一半”）以此为前提 |
| 0.2 | DSpark 到底能不能跑 | E18 写 V4.1 DSpark 多步投机 16 GB 连续段 OOM、BLOCKED；model-test D7 写 DSpark 1800/1800 成功、TPOT 降 49%/64% | 对比两次的启动命令：`num_speculative_tokens`、`enable_adaptive_verification`、`gpu-memory-utilization`、`max-num-batched-tokens` | AR-07 需要一个确定能跑的配置 |
| 0.3 | V4.1 每 token 的 KV 到底多大 | 记录：满 1M 请求约 34 GiB → 平均约 34.8 KiB/token；`09` 第 167、172 行：全局 KV 约 890 字节/token（CSA2 跨层复用 + **FP4 KV**） | 见 AR-01 第 3 步 | `09` 据 890 B/token 推出“512 条 × 8k 的教师 KV 只要约 3.6 GB”，并据此限定 I8 的适用范围。若实测偏差大，这个结论要改 |

**对 0.3 的初步推测（待 AR-01 验证）**：MLA 类的潜向量 KV 在张量并行下不按头切分，8 个 rank 每个都存一份完整 KV。如果 34 GiB 是 8 个 rank 的合计，折合每个 rank 约 4.3 KiB/token；H800 不支持 FP4 KV（E10 的 nvfp4 为 BLOCKED），若实际用 BF16，890 B × 4 ≈ 3.5 KiB，再加上滑动窗口和 indexer 的缓存，量级大致吻合。若推测成立，对 I8 的影响是：**512 × 8k ≈ 419 万 token，每个 rank 约需 18 GiB 教师 KV**，而 V4.1 在 TP8 下每卡留给 KV 的空间只有十几 GiB 量级，教师 KV 并不是“可以忽略”。

## 1. 通用做法

1. **先算后测**：每个实验先根据 `config.json` 写出预期值（参数量、FLOPs、KV 字节、通信量），再实测。偏差超过 20% 就要找到原因，这一步最能帮助理解架构。
2. **一次只改一个变量**，其余沿用 `experiments/workloads.sh` 的标准负载和 README 第 1 节的约定（每个配置至少 2 次）。
3. **记录**：结果放 `runtime/results/AR-xx/`，`notes.md` 按 `TEMPLATE-实验记录.md` 写；启动日志用 `tools/parse_server_log.py` 提取权重、KV 池、CUDA graph 信息。
4. **模型**：V4.1 = `dsv41-flash`，GLM-5.3 = `glm53-flash`，GLM-4.7 = `glm47-flash`，Qwen3-8B = `qwen3-8b`。Qwen3-32B 在 E22 部署过，本包没有 profile，复制 `qwen3-8b.sh` 改 `MODEL_KEY`。

## AR-01 从 config.json 推出“每个 token 花多少”

**目的**：在测量之前就知道该看到什么。能算准之后，后面每个实验都有对照值。

**做法**：

1. 读每个模型的 `config.json`（只读），写一张表：层数、隐藏维度、注意力类型与头数、KV 维度、专家数与每 token 激活专家数、共享专家、词表大小。
2. 估算每 token 的激活参数量和前向 FLOPs（约 2 × 激活参数），以及每 token 每层的 KV 字节：
   - GQA：`2 × KV头数 × head_dim × 字节数`
   - MLA：`(kv_lora_rank + qk_rope_head_dim) × 字节数`，张量并行下**每个 rank 存全量**
   - KDA / 线性注意力层：不随长度增长，每个请求一份固定大小的状态
   - 滑动窗口层：长度超过窗口后不再增长
3. **用已有数据核对**：
   - Qwen3-8B 示范：36 层 × 8 个 KV 头 × 128 × 2（K、V）× 2 B = 147,456 B ≈ 144 KiB/token；E13/E10 实测 53.41 GiB 的池放下 388,896 个 token，折合 ≈ 144 KiB/token，**完全吻合**。
   - V4.1：用 `parse_server_log.py` 从启动日志取**每个 rank** 的 KV 池 GiB、KV token 数和 KV dtype，算出每 rank 的字节/token，与 890 B（FP4）和 34.8 KiB（记录折算）对比，回答第 0.3 节。
   - GLM-5.3：同上，另记 KDA 状态池的大小（E13-F）。

**回传**：每个模型一行“理论值 / 实测值 / 偏差原因”。

**判断**：V4.1 每 rank 的实测值 ≥ 2 KiB/token 时，在 `09` 第 172 行旁注明“H800 上非 FP4 KV、TP 下每 rank 全量”，并按实测值重算 I8 的教师 KV 账。

## AR-02 四种注意力设计的 KV 账本与长度扫描

**目的**：直接看到“为什么新模型要用滑动窗口、压缩稀疏和线性注意力”。

| 模型 | 注意力设计 | 预期 |
|---|---|---|
| Qwen3-8B | GQA | KV 随长度线性增长；TPOT 随长度明显上升 |
| GLM-4.7-Flash | MLA | KV 线性增长，但斜率远小于同规模 GQA |
| GLM-5.3-Flash | 34 层 KDA + 11 层稀疏 MLA（indexer 取 top-2048） | KV 增长斜率约为同结构纯 MLA 的 11/45；TPOT 接近持平 |
| DeepSeek-V4.1-Flash | 滑动窗口 + 压缩稀疏注意力 + 两级 indexer | 平均每 token 的 KV 随长度下降；TPOT 最平 |

**做法**：单请求，输入 4K / 32K / 128K（Qwen3-8B 只到 32K；V4.1 另加 512K），输出 256。每个长度记录 `/metrics` 中 KV 用量的增量、TTFT、TPOT。命令沿用 E23-D：

```bash
for L in 4096 32768 131072; do
  bash scripts/bench_serve.sh --tool vllm --exp AR-02 --label glm53-ctx$L --instance vllm-glm53-flash -- \
    --dataset-name random --random-input-len $L --random-output-len 256 --ignore-eos --num-prompts 4 --max-concurrency 1 --seed 1
done
```

128K 输入要求 `--max-model-len` ≥ 131072 + 256，必要时在启动命令的 `--` 之后追加。

**回传**：两张图：“KV 字节 vs 输入长度”“TPOT vs 输入长度”，四个模型各一条线。

**判断**：GLM-5.3 的 KV 斜率偏离 11/45 预期超过 30%，或 V4.1 的 TPOT 在 128K 时比 4K 高 50% 以上，就说明还有没算进去的结构（例如 indexer 缓存），回到 AR-01 补上。

## AR-03 不同长度和 batch 下的耗时拆分

**目的**：知道上下文变长、batch 变大时，时间花在哪一块，这正是稀疏 indexer 和 mHC 的设计动机所在。

**已有数据**：E16（qwen3-8b，BS16 decode）GEMM 79%、attention 12.4%；E17（V4.1，8 rank）MoE/GEMM 47.7%、attention 13.8%、mHC 11.4%、通信 9.8%，但只有一个配置。

**做法**：V4.1 与 GLM-5.3，输入 {8K, 128K} × decode batch {1, 16, 64}，外加一次纯预填充（8K、batch 1）。采集方法见 E16（vLLM `--profiler-config` + `/start_profile`）。分析：

```bash
runtime/envs/client/bin/python tools/analyze_torch_trace.py runtime/traces/AR-03/<名字>/*.pt.trace.json.gz \
  --md runtime/results/AR-03/<名字>.md --json runtime/results/AR-03/<名字>.json
```

把 kernel 归成六类：indexer、attention、MoE GEMM（含路由）、dense GEMM、mHC、通信。

**回传**：12 个配置 × 6 类的占比表，以及每个配置 <50% SM 覆盖的时间占比。

**判断**：128K 时 indexer + attention 的占比是否超过 MoE；batch 1 时 SM 覆盖率低于 50% 的时间是否超过 30%（R6 的证据）。

## AR-04 MoE 的 batch 扫描与专家覆盖

**目的**：理解为什么 MoE 计算量小、却需要大 batch 和 EP。batch 小时，每一步都要读很多专家的权重，却只算几个 token；batch 变大后读进来的专家被更多 token 共用。

**预期（先算）**：V4.1 每层 384 选 6。batch 为 B 时，一层中被至少一个 token 选中的专家数期望约为 `384 × (1 − (1 − 6/384)^B)`（假设均匀路由）：B = 1 时 6 个，B = 64 时约 244 个，B = 256 时约 377 个。读权重的量随这个数增长，吞吐的拐点应出现在专家基本全覆盖之后。GLM-5.3 按 288 选 8 同样计算。

**做法**：

1. decode 并发 {1, 2, 4, 8, 16, 32, 64, 128}，输入 1K、输出 512，记录 TPOT 与输出吞吐。
2. 同样扫 Qwen3-32B（稠密对照）。
3. 用 SGLang 的专家分布记录器（见 `tools/expert_stats.py` 文件头）记录每步被激活的专家；vLLM 需要 `--enable-return-routed-experts`（E06 已确认 V4.1 的 `/metrics` 里没有专家指标）。

**回传**：“每步激活的不同专家数 vs batch”（实测与均匀假设各一条线）、“TPOT vs batch”（MoE 与稠密对照）。

**判断**：实测的专家覆盖比均匀假设低得多，说明路由有强局部性（与 E06 的均衡度 0.41–0.49 对照），这对专家预取、卸载有用（R8、R-A+）。

## AR-05 训推一致性：近似计算对 logprob 的影响（即 `09` 的 P4）

**目的**：理解“推理端的近似”会不会改变教师打分。E09 显示 FP8 权重下逐字一致率只有 3%，但没量化 logprob 层面的偏差。

**做法**：固定 100 条“提示 + 回答”（用 E22 数学题的模型输出），请求 prompt logprobs（top-k = 0 与 20），比较：

| 对比 | 模型 | 开关 |
|---|---|---|
| SWA 有界重放 开 / 关 | V4.1 | vLLM `--no-swa-bounded-replay`；SGLang `--no-enable-decoder-swa-bounded-replay`（E23-E） |
| KV dtype BF16 / FP8 | Qwen3-8B | `--kv-cache-dtype fp8`（E10） |
| 权重 BF16 / 在线 FP8 | Qwen3-8B | `--quantization fp8`（E09） |
| 一次性预填充 / 256 与 1k 分块增量预填充、TP1/2/4 | Qwen3-8B | 按 `09` 第 6.2 节 P4 |

**回传**：每个对比的逐 token 绝对差分布（p50、p99、最大值）、top-1 一致率、按序列平均的 KL。

**判断**（沿用 P4）：分块与一次性的差异落在 TP 差异范围内，I8 可以写“目标函数不变”；超出则改写为“误差有界”。

## AR-06 EP 负载均衡（补 E05）

**目的**：理解专家并行的拖尾从哪里来。E06 已证明专家激活随任务类型变化。

**做法**：GLM-4.7-Flash（64 选 4，是本包 EP 实验的主力），EP4 或 EP8。负载前 5 分钟全是数学，然后突然切到代码。对比 EPLB 关、开（窗口取默认和较短两档）。

**回传**：每个 rank 的 token 数之比（max/mean）随时间的曲线、TPOT p99。

**判断**：切换后 max/mean 的恢复时间是否明显长于 EPLB 的统计窗口（R8 的证据）。

## AR-07 投机解码的收益拐点

**目的**：MTP 和 DSpark 是做进模型本体的草稿头。看它在什么负载下有用、什么时候反而拖累。

**做法**：

1. GLM-5.3 MTP（profile `glm53-flash-mtp`）：G5 已测并发 1（吞吐 1.57–1.68×），补测并发 8、32、64。
2. V4.1 DSpark：先按第 0.2 节确定能跑的配置，再按任务分组（数学、代码、闲聊、智能体轨迹）测接受长度；可选对比 `enable_adaptive_verification` 开 / 关（E23-B）。

**回传**：每个并发下“开投机 / 不开”的吞吐比与 TPOT；每类任务的平均接受长度。

**判断**：吞吐比降到 1.0 以下的并发值即收益拐点；把它与 rollout 长尾阶段的实际并发对照（R3）。

## AR-08 Engram 主机表的代价（补 E23-A）

**目的**：Engram 的两张 n-gram 表约 183 GiB，只查表不计算。看它放在主机内存时，预填充和解码各付出多少。

**预期（先算）**：查表次数与 token 数成正比，所以预填充最吃 PCIe，解码影响小。

**做法**：V4.1 默认 profile（Engram 在主机内存），输入 {1K, 8K, 32K}、输出 256，单请求和并发 8 各测一次。同时在另一个终端运行 `nvidia-smi dmon -s t -d 1 > runtime/results/AR-08/pcie-<标签>.log` 记录 PCIe 收发带宽。

**回传**：每个配置的 TTFT、TPOT、PCIe 峰值与平均带宽；与 W1 实测的 PCIe 带宽（`09` W1 的 T0）对照。

**判断**：预填充时 PCIe 带宽是否接近实测上限（是则查表在关键路径上，R-D 值得做）。

## AR-09 单机 PD 分离（重试 E14）

**目的**：E14 标为 BLOCKED 的理由是“没有 RDMA 多机”，但单机内可以用 4 卡做预填充、4 卡做解码，KV 走 NVLink/CUDA IPC 传输（例如 vLLM 的 NixlConnector 单机模式，或 SGLang 的 PD 分离）。**能否跑通需要实测确认**。

**做法**：用本包已有的 `*-pd-prefill.sh` / `*-pd-decode.sh` profile（GLM-4.7 或 Qwen3-8B），与同卡数的普通部署对比：混合负载（长提示 + 短提示）下的 TTFT、ITL p99、goodput（E20 的 SLO 口径）。

**回传**：能否启动；KV 传输耗时占 TTFT 的比例；与普通部署的 goodput 对比。

## AR-10 思考强度曲线（补 E23-C）

**目的**：思考预算也是模型设计的一部分。E22 中 V4.1 的 GPQA 在 8k 预算下从 86% 掉到 68%，说明预算影响很大。

**做法**：V4.1 强度 {10, 25, 50, 75, 100}，GLM-5.3 取 {low, high, max}；数据用 E22 的 AIME25 或 MATH-500，命令见 E23-C。

**回传**：强度 → 正确率、平均输出 token 数、“每答对一题的 token 成本”。

**判断**：技术报告称 60–80 能以不到一半的 token 恢复大部分精度，看实测是否成立（R9）。
